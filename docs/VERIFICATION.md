# 검증 현황

단계마다 갱신한다. "확인"은 실제 기기에서 인증된 API 호출로 본 것이고, "미확인"은 아직 보지 못한 것이다.
예약 상태는 DB를 직접 바꾸지 않고 보호소 테스트 계정과 승인 API로 만든다.

## 테스트 환경 (2026-11-25)
- 로컬 BE(`walkwithdog-BE`, dev 브랜치)와 로컬 PostgreSQL
- 주의: 지금까지의 테스트 산책은 예약 3번의 산책 1번뿐이고 11초(09:02:24~09:02:35 UTC)였다. 짧은 산책으로는 정지·마커·신고·좌표 전송을 확인할 수 없다.
- 다음 테스트 산책(레벨업 횟수를 채우는 산책)은 2~3분 걷고, 7단계 "미확인(더 긴 테스트 산책이 필요함)" 항목을 함께 확인한다.
- 실제 기기에서 Expo Go로 FE 실행
- 보호소 계정 `shelter01`을 Swagger에서 사용해 일정 생성, 예약 승인, 보호소 코드 발급
- 예약 3번(승인 상태)으로 보호소 코드부터 산책 종료까지 진행

## 6단계 내 예약, 취소 (8-1~8-8)

### 기기에서 확인함
- 내 예약 목록 불러오기와 "승인 대기" 카드 표시(시각은 KST)
- 대기 중인 예약 취소 흐름(8-4 → 8-7 → BottomSheet 확인 → 8-8)
- 취소 뒤 목록의 "지난 예약" 탭 반영
- 이미 취소된 예약의 안내 문구(409 `REQUEST_ALREADY_CANCELLED`)
- 승인 상태 상세 화면(8-3)

### 미확인
- 취소 오류 경로: `CANCEL_TIME_EXPIRED`, `WALK_RECORD_EXISTS`, `REQUEST_STATE_CONFLICT`, `REQUEST_LOCK_CONFLICT`
  (`REQUEST_ALREADY_CANCELLED`는 API 재전송으로 따로 확인한다)
- 한 페이지(20건)를 넘는 목록: 더보기, offset을 원본 개수만큼 더하는 동작, 예약 ID 중복 제거
- 승인 뒤 취소
- 403과 404 처리: HTTP 상태로만 나눈다. 나이 확인 대기 계정은 `GET /users/me`의 단계로 판단한다.
- 확정 탭에 산책을 마친 예약이 "산책 완료"로 보이는지
- 예약 취소 뒤 목록 캐시 무효화: 취소 뒤 뒤로 돌아간 목록이 첫 페이지부터 다시 불러와지는지

## 7단계 보호소 코드, 시작, 산책 중, 신고, 종료 (4-x, 5-x)

### 기기에서 확인함
테스트 산책(예약 3번, 산책 1번)은 09:02:24~09:02:35 UTC, 즉 11초였다. 11초 안에 할 수 있는 것만 확인으로 둔다.
- 보호소 코드 입력(4-1)과 산책 시작(체크리스트 4-4 → 5-1)
- 위치 권한 요청과 허용
- 산책 시간이 계속 늘어남
- 산책 종료와 6-1로 이동

### 미확인 (더 긴 테스트 산책이 필요함)
이전에 확인으로 적었으나 11초 산책으로는 해 볼 수 없어 되돌렸다. 다음 테스트 산책은 2~3분 걷고 아래를 모두 포함한다.
- 일시정지와 이어 걷기: 정지 중에도 시간이 계속 늘고 "일시정지됨"만 표시되는지, 이어 걷기가 되는지
- 정지 중에 신고 시트와 마커 메뉴를 열고 닫아도 정지 상태가 바뀌지 않는지
- 마커 4종 저장: 냄새 맡기, 배변, 다른 개, 포토스팟(`OTHER` + 메모 "포토스팟")
- 비행기 모드 뒤 같은 마커 재시도에서 중복 저장되지 않는지
- 신고 전송과 결과 화면(5-6, 5-7)
- 화면 잠금 뒤 돌아오기
- 앱을 완전히 종료한 뒤 홈에서 진행 중인 산책 복구
- 6-2에 실제 경로(폴리라인)와 마커가 그려지는지(좌표가 쌓일 만큼 걸어야 한다)

### 미확인 (그 밖)
- 자동 종료(`AUTO_TIMEOUT`)와 그 뒤의 복구 경로(안내 문구, 6-1 이동, 보내지 못한 좌표 안내, 종료 뒤 좌표 전송 차단)
- 기기 시계가 서버보다 앞서거나 뒤일 때의 좌표 전송과 마커, 신고 전송
- 종료 응답이 유실됐을 때 같은 산책의 상세로 확인하는지
- 산책 중 세션 만료와 다시 로그인 뒤 같은 산책으로 돌아오기
- 1시간을 넘기는 일시정지(정지 중에는 좌표가 없어 서버가 자동 종료한다)
- 오래 오프라인으로 걷는 경우(메모리 큐, 순번 연속 유지, 앱 종료 시 큐 유실)
- 보호소 코드 5회 실패 잠금(429 `SHELTER_CODE_RATE_LIMITED`)
- 위의 6단계 미확인 중 "한 페이지를 넘는 목록", "취소 오류 경로"
- 이번 기기 테스트에서 따로 기록하지 않은 항목: 틀린 코드(422)와 만료 코드, 위치 권한 거부, GPS 끊김 자동 안내(30초 무신호)와
  위치 다시 연결, 신고 실패 뒤 "다시 전송하기", `DUPLICATE_RECENT` 확인, 위치가 없는 마커(`MARKER_LOCATION_UNAVAILABLE`),
  좌표 순번과 재전송 동작, 정지와 재개 사이 간격이 선으로 이어지지 않는지

### 알려진 한계
- 앱이 foreground일 때만 위치를 모은다. 백그라운드에서는 수집이 끊기고 서버가 새 좌표 없이 1시간이 지나면 자동 종료한다.
- 보내지 못한 좌표 큐는 메모리에만 있다. 앱 프로세스가 종료되면 사라진다(저장소 도입 여부는 별도 결정).
- 지도는 목업 그림이고 실제 경로는 그리지 않는다. 6-x 이후 화면은 목업이다(8단계). 종료 결과는 `getEndedWalk()`에 남는다.

### 기기 시계와 좌표 시각
좌표의 `recorded_at`은 기기가 위치를 얻은 실제 시각 그대로 보낸다. 서버는 시작 이후, 서버 현재 시각 이하만 받고
위반하면 batch 전체를 409로 거절한다. 기기가 앞서면 서버 시각이 그 시각을 지날 때까지 큐에 두고, 뒤면
시작 이전 관측은 보내지 않는다. 서버 시각은 `GET /walks/active`의 `elapsed_seconds`로 추정하고 5분마다 다시 맞춘다.
이 처리는 아직 기기에서 확인하지 않았다.

## 8단계 인계, 기록 저장, 레벨업, 이력 (6-1~6-3, 9-1, 9-2)

구현했고 타입 검사만 통과했다. 기기에서는 아직 아무것도 확인하지 않았다.
테스트 데이터: 예약 3번의 산책(종료됨, 인계 전)으로 인계, 메모, 이력을 확인한다.

### 기기에서 확인함
- 없음

### 미확인
- 6-1 정상 인계: 세 항목을 체크하고 접수(201), 접수 뒤 6-2로 이동
- 6-1 같은 내용 재전송이 200으로 이어지는지(응답 유실 뒤 같은 본문으로 다시 누르기), 다른 내용을 보내면 409 처리
- 6-1 "인계에 문제가 있어요" 접수(문제 내용 1~500자, 미완료 항목이 하나 이상 있어야 함)
- 6-1 자동 종료(`AUTO_TIMEOUT`) 산책의 확인 안내와 `acknowledge_auto_timeout` 전송
- 6-1 중단된 산책(문제 접수만 가능한 화면)
- 6-2 서버 확정 통계(총 시간, 거리, 평균 속도)와 날짜(KST), 실제 경로 폴리라인과 마커 표시
- 6-2 경로가 끊기는지: 정지·재개 사이(15초 초과), 정확도가 나쁜 좌표(20m 초과나 없음), 비정상 속도(5m/s 초과), 페이지(500개) 경계. 좌표가 없는 산책에서 자리 표시 지도만 나오는지
- 6-2 메모 저장(최초 201, 수정 200), 같은 메모 재저장, 메모 버전 충돌(409), 빈 메모는 저장하지 않음
- 6-2 메모 규칙: 인계 전(NOT_CONFIRMED)이면 막고 인계 안내, 첫 저장은 expected_version=0, 수정은 서버 버전, 응답 유실이나 409 뒤에 서버 메모를 보여 주고 선택하게 하는지(조용히 덮어쓰지 않는다)
- 6-2 메모는 선택: 메모 없이 저장해도 레벨 평가로 넘어가는지, 인계가 필요 없는 산책(NOT_REQUIRED)은 인계 버튼 없이 메모만 되는지
- 6-2 저장 뒤 레벨 평가 확인(3초 간격, 약 60초): PENDING은 "레벨을 평가하는 중", FAILED는 "지연", 끝내 끝나지 않으면 이력으로 이동하고 나중에 다시 확인
- 6-3 레벨업 화면과 서버 레벨 표시(BE `.env`에 레벨 정책 변수를 넣은 뒤)
- 9-1 서버 이력 목록, 통계 카드(`history_walk_count`, `history_distance_m`, 거리 일부 미확인 표시), 빈 목록, 오류와 다시 시도, 당겨서 새로고침
- 9-1 한 페이지(20건)를 넘는 목록과 더보기(마지막 페이지 판단에 서버 `total`도 함께 사용), 인계·메모 저장 뒤 목록 새로고침
- 9-1 "인계 필요" 필터: 인계 전 산책 수(서버 `total`), 항목을 누르면 6-1이 열리는지
- 9-1을 다시 볼 때 평가가 끝나지 않았던 산책의 레벨 결과를 다시 확인하는지
- 같은 레벨업을 다시 보여 주지 않는지(계정 ID와 이벤트 ID를 `expo-secure-store`에 기억), 앱 재시작 뒤에도 유지되는지
- 6-3 문구("꾸준한 산책으로 새로운 레벨을 달성했어요.")와 서버 레벨 숫자(`after_level`)
- 9-2 상세(메모, 기록한 항목 개수, 인계 상태), 인계 전 산책의 "인계 확인하기"
- 자동 종료와 직원 중단 산책에서 레벨업이 나오지 않는지

### 레벨업 로컬 테스트 계획
레벨은 성취 지표일 뿐이며 예약 권한, 강아지 크기, 난이도와 무관하다.

- **사전 설정(걷기 전에 해야 한다):** 로컬 BE `.env`에 `VOLUNTEER_LEVEL_POLICY_VERSION`과 `VOLUNTEER_LEVEL_POLICY_START_AT`(UTC)을
  넣고 BE를 재시작한 뒤에 산책을 시작한다. 현재 값은 `local-level-v1`, `2026-11-25T00:00:00+00:00`이다.
- **반영되는 산책:** 정책 시작 이후에 시작했고, `COMPLETED`이며, 종료 사유가 `USER`이고, 인계가 `SELF_REPORTED`(정상 인계)이며,
  같은 계정의 산책이다. 최소 시간, 거리, 좌표 수 조건은 없다. 같은 산책은 두 번 반영되지 않는다.
- **제외되는 산책:** 자동 종료(`AUTO_TIMEOUT`), 직원 중단, 정책 시작 이전 산책, 문제 접수(`ISSUE_REPORTED`) 인계.
  문제 접수로 낸 인계는 나중에 반영 대상으로 바꿀 수 없다.
- **레벨 기준(반영 산책 수, 평가 중인 산책 포함, 줄지 않는다):** Lv.1 = 0~2, Lv.2 = 3~9, Lv.3 = 10~19, Lv.4 = 20~39, Lv.5 = 40 이상.
- **레벨 2까지의 산책 수:** 정상 인계를 마친 산책 3번. 예약 3번의 산책이 1번째이고 2번 더 걷는다.
  각 산책마다 일정 만들기, 신청, 승인, 코드 발급(`shelter01`)을 반복하고, 인계는 반드시 세 항목을 모두 체크한 정상 인계로 한다.
- **기대 결과:**
  - 1번째와 2번째 산책: 인계 뒤 6-2 저장 때 평가가 `PENDING`을 거쳐 `COMPLETED`(레벨업 없음)가 되고 6-3은 열리지 않는다.
  - 3번째 산책: `COMPLETED` + `level_up_event`가 오고 6-3에 "산책 레벨 2"가 나온다. 9-1을 다시 열거나 앱을 다시 시작해도 같은 6-3이 또 나오지 않는다.
  - 평가 작업은 30초마다 돌아 몇 초에서 수십 초 걸린다. 약 60초 안에 끝나지 않으면 이력으로 넘어가고 9-1을 다시 볼 때 결과를 확인한다.
- **제외 확인(선택, 산책 3번 더):** 자동 종료 산책(`AUTO_END_AFTER_SECONDS`를 짧게), 직원 중단 또는 문제 접수 인계 산책에서 레벨업이 나오지 않는지.
- **총 필요한 산책:** 레벨 2 확인 3번. 제외 확인까지 하면 최대 6번.

## 통계 필드 매핑 (확정)
`GET /volunteers/me`의 `history_*`(종료한 모든 산책 = COMPLETED + INTERRUPTED, 자동 종료 포함)를 9-1과 10-1 모두에 쓴다.
9-1 목록과 같은 범위라 숫자를 목록과 맞춰 볼 수 있다. 9단계(10-1 마이페이지)도 같은 필드를 쓴다.

| 숫자 | 필드 | 비고 |
|---|---|---|
| 총 산책 | `history_walk_count` | 9-1 카드, 10-1 카드 |
| 총 거리 | `history_distance_m` | `history_distance_is_complete`가 false면 "일부 미확인"을 함께 표시한다(거리가 없는 산책은 합계에서 빠진다) |
| 함께한 강아지 | `history_unique_dog_count` | 10-1 카드 |
| 레벨 | `level` | 10-1 배지. 서버가 평가해 올리는 값이다 |

- 총 시간(`total_duration_seconds`)은 표시하지 않는다.
- 이전 봉사 기록 합계(`total_walk_count`, `total_distance_m`, `unique_dog_count`)는 화면에 쓰지 않는다.
- 레벨 반영 산책 수를 `total_walk_count`나 `history_walk_count`로 추정하지 않는다. 레벨은 서버의 평가 결과만 따른다.
- 기기 확인: 9-1 카드는 위 필드로 바꿨고 아직 기기에서 확인하지 않았다. 10-1은 9단계에서 같은 필드로 연결한다.

- 10-1 마이페이지가 서버 값(닉네임, 통계, 레벨)을 보여 주고 당겨서 새로고침이 된다
- 마이페이지에서 로그아웃한 뒤 다시 로그인할 수 있다

**기대가 틀렸던 점검 (BE 동작은 정상)**
- *다른 계정이 쓰는 번호로 인증:* 처음에는 "인증은 통과하고 저장에서 409"를 기대했지만, BE는 이미 등록된 번호의 요청을 보내지 않은 것으로 저장하고(`SUPPRESSED`)
  절대 인증되지 않게 한다(#110, 번호 등록 여부를 숨기려는 정책). 그래서 발송은 200이지만 **인증번호 확인이 422 `VERIFICATION_CODE_INVALID`**가 되고,
  그 id로 저장하면 409 `PHONE_VERIFICATION_REQUIRED`다. 앱에서는 "인증번호가 맞지 않아요"로 보이며 5번 틀리면 429 `VERIFICATION_ATTEMPTS_EXCEEDED`다.
  `PHONE_ALREADY_REGISTERED`는 인증을 먼저 마친 뒤 다른 계정이 그 번호를 등록한 경우에만 나오며, 위 표의 해당 줄은 그 경우를 따로 만들어 확인했다.
- *짧은 인증번호:* 6자리가 아니면 422 `INVALID_VERIFICATION_PAYLOAD`다(형식 검사). 앱은 6자리가 아니면 보내지 않고 같은 문구를 보여 준다.

**코드별 문구와 화면 처리 점검:** 위에서 본 코드는 모두 `errorMessages.ts`에 문구가 있다. 예외는 `INVALID_ACCESS_TOKEN` 하나로, 문구는 없지만 401을
HTTP 상태로 처리한다(클라이언트가 토큰을 지우고 로그인 화면으로 보내며, 로그아웃은 401을 정상으로 본다). 핸들러가 없는 코드는 없다.
`INVALID_PROFILE_PAYLOAD`, `INVALID_DURATION`, `INVALID_DOG_SIZE`, `INVALID_PREFERENCE_PAYLOAD`, `VERIFICATION_CODE_INVALID`는 화면에 전용 분기는 없고
기본 경로(`errorMessage(code)`)로 문구를 보여 준다.

**API 수준에서도 아직 확인하지 않은 것:** 인증번호 만료(410, 5분 대기 필요), 확인 뒤 15분이 지난 인증, 인증 시도 5회 초과(429), 발송 일일 한도와 재발송 대기(429), 이름 변경 시 Step 1 없는 계정(409).

### 미확인 (앱 화면에서)
- 10-1 마이페이지: 거리 일부 미확인 표시(`history_distance_is_complete`가 false일 때), 로딩, 오류와 다시 시도, 내 정보 수정에서 돌아오면 닉네임 갱신
  (닉네임, 통계 카드, 레벨, 당겨서 새로고침은 위에서 확인함)
- 10-2 내 정보 수정: 프로필 불러오기, 닉네임 변경 저장, 이름 변경 저장(온보딩 Step 1을 마친 계정), 바뀐 필드만 전송, 저장 응답 뒤에 화면 닫기
- 10-2 번호 변경 전 과정: 새 번호 입력, 인증 요청(`/users/me/profile/phone-verifications`), 인증번호 확인, 저장(`phone_number` + `phone_verification_id`)
- 10-2 번호 변경 오류: 다른 계정이 쓰는 번호(인증번호 확인이 422 `VERIFICATION_CODE_INVALID`로 실패), 인증 없이 저장(409 `PHONE_VERIFICATION_REQUIRED`),
  틀린 인증번호(422 `VERIFICATION_CODE_INVALID`), 만료(410), 15분이 지난 인증, 닉네임 중복(409 `NICKNAME_ALREADY_EXISTS`).
  `PHONE_ALREADY_REGISTERED` 화면 처리는 API로만 만들 수 있다(인증을 마친 뒤 다른 계정이 그 번호를 등록해야 함)
- 10-2 버전 충돌(409 `PROFILE_VERSION_MISMATCH`): 최신 프로필을 보여 주고 "서버 값 보기 / 내 입력으로 저장 / 닫기"를 고르게 하는지(조용히 덮어쓰지 않는다)
- 10-3 산책 선호: 불러오기(저장값 없으면 온보딩 값), 저장, 버전 충돌(409 `PREFERENCE_VERSION_MISMATCH`)과 선택 화면, 저장 응답 뒤에 화면 닫기
- 설정 화면: "목업" 문구가 없는지, 로그아웃 행
- 로그아웃(마이페이지와 설정): 서버 호출 뒤 토큰과 로컬 상태 삭제, 같은 계정으로 다시 로그인했을 때 이전 상태(산책, 예약, 이력, 임시 입력)가 남지 않는지
  (마이페이지에서 로그아웃한 뒤 다시 로그인되는 것까지만 위에서 확인함. 설정 화면의 로그아웃은 확인하지 않았다)
- 로그아웃 중 서버에 닿지 않을 때(비행기 모드): 이 기기에서만 로그아웃했다는 안내 뒤에도 로컬 상태가 지워지는지
- 산책 중이고 보내지 못한 위치 기록이 있을 때 "그래도 로그아웃 (미전송 기록 삭제)" 확인이 한 번 더 뜨고, 그것을 고르면 로그아웃되는지.
  그 밖의 경우(산책 중이어도 보내지 못한 기록이 없을 때 포함)는 확인 한 번으로 바로 로그아웃되는지
- 본 레벨업 기록(`levelUpSeen`)이 로그아웃 뒤에도 계정별로 남는지

### 통계 매핑 적용
10-1은 위 "통계 필드 매핑(확정)"과 같다: 총 산책 `history_walk_count`, 총 거리 `history_distance_m`(미확인 표시 포함),
함께한 강아지 `history_unique_dog_count`, 레벨 `level`. `total_*`와 `total_duration_seconds`는 쓰지 않는다.

### 테스트 데이터 준비
스크립트가 임시 계정을 만들었다(비밀번호는 저장하지 않았으므로 이 계정들로는 로그인할 수 없다). 현재 로컬 DB(2026-11-25):

| 계정 | 닉네임 | 번호 | 프로필 버전 |
|---|---|---|---|
| `snsns`(앱 테스트용) | `eksks` | 010-0000-0001 | 1 |
| `tmpb82blej` | `tmp_b_1pct` | 010-0000-0003 | 1 |
| `tmpahj1q0z` | `tmp_a2_1pct` | 010-0000-0002 | 4 |
| `tmpc6ixv3k` | `tmp_c_6ixv3k` | 010-0000-0006 | 1 |
| `tmpdc3fj64` | `tmp_d_c3fj64` | 010-0000-0007 | 1 |

산책 선호는 `snsns`에 저장된 행이 없다(버전 0). 번호는 합성 번호 010-0000-0000~9999만 쓸 수 있고, 로컬 BE의 고정 인증번호는 `123456`이다.
010-0000-0002는 이제 임시 계정이 쓰고 있어 앱 테스트에는 쓸 수 없다.

1. 번호 변경 성공: `snsns`로 새 번호 `010-0000-0008`로 변경한다(인증번호 `123456`). 변경 뒤 10-2에 새 번호가 보이고 프로필 버전이 올라가야 한다.
2. 다른 계정이 쓰는 번호: `010-0000-0003`(또는 0002, 0006, 0007)으로 인증을 요청하면 발송은 200이지만 인증번호 확인이 "인증번호가 맞지 않아요"로 실패해야 한다
   (BE가 등록 여부를 숨기려고 일부러 인증되지 않게 한다. 5번 틀리면 429).
3. 프로필 버전 충돌: 앱에서 10-2를 연 채로, Swagger에서 `snsns` 토큰으로 `GET /users/me/profile`을 읽어 `profile_version`을 확인한 뒤
   `PATCH /users/me/profile` `{"expected_profile_version":<현재 값>,"nickname":"conflict_nick"}`을 한 번 보낸다. 앱에서 다른 값을 고쳐 저장하면 409가 나와야 한다.
4. 선호 버전 충돌: 앱에서 10-3을 연 채로 Swagger에서 `PATCH /users/me/walk-preferences` `{"expected_version":0,"duration_code":"OVER_60_MIN"}`을 한 번 보낸다
   (저장된 행이 없어 버전 0이다). 앱에서 저장하면 409가 나와야 한다.
5. 닉네임 중복: 앱에서 10-2 닉네임을 `tmp_b_1pct`로 바꿔 저장하면 409(`NICKNAME_ALREADY_EXISTS`)가 나와야 한다.

### 문서와 코드 차이 (BE 담당자에게 알릴 것)
- **프로필 번호 인증 경로:** 문서(`docs/HANDOFF-FE.md` 4.7, 5절)는 `/users/me/phone-verifications`라고 적었지만, 그것은 온보딩 인증 경로다.
  프로필 번호 변경은 `POST /users/me/profile/phone-verifications`(발송)와 `POST /users/me/profile/phone-verifications/confirm`(확인)을 쓴다.
  FE는 코드 기준인 프로필 경로를 쓴다. 문서의 "프로필 번호 변경도 같은 방식"이라는 문장이 경로까지 같다는 뜻으로 읽히지 않게 고쳐야 한다.
- **문서에 없는 오류 코드:**
  - 프로필 `PATCH`: 403 `PROFILE_UPDATE_NOT_ALLOWED`, 409 `PROFILE_BASIC_INFO_REQUIRED`, 422 `INVALID_PROFILE_PAYLOAD`, `NICKNAME_REQUIRED`, `REQUIRED_FIELD`
    (문서는 `PROFILE_VERSION_MISMATCH`만 적었다. `NICKNAME_ALREADY_EXISTS`, `PHONE_VERIFICATION_REQUIRED`, `PHONE_ALREADY_REGISTERED`도 코드에만 있다)
  - 프로필 인증 확인: 422 `INVALID_VERIFICATION_PAYLOAD`
  - 선호 `PATCH`: 403 `PREFERENCE_NOT_ALLOWED`, 422 `INVALID_PREFERENCE_PAYLOAD`, `INVALID_DURATION`
    (문서는 `PREFERENCE_VERSION_MISMATCH`만 적었다. 코드에서는 저장값이 같아도 버전이 다르면 409다)
- **선호에는 지역이 없다:** 코드의 선호는 `duration_code`와 `size_code`뿐이고, `region_code` 등 다른 필드를 보내면 422다.
  FE의 10-3은 지역을 저장하지 않고 "온보딩에서 고른 지역"이라는 고정 문구만 보여 준다. 문서의 지역 관련 설명(과 Notion 일부 명세)을 코드에 맞춰야 한다.

## 5-1, 6-2 카카오 웹 지도: 경로, 마커, 카메라 따라가기

구현했고 타입 검사를 통과했다. 아래는 모두 **구현함, 기기에서 확인하지 않음 (NOT VERIFIED)**이다. 같은 플래그(`EXPO_PUBLIC_WALK_MAP_KAKAO_WEB=true`)로만 켜지고, 키가 없거나 8초 안에 열리지 않으면 기존 자리 표시 지도로 돌아간다.

### 구현함, 기기에서 미확인
- 5-1 경로 선: 걸은 좌표를 선으로 그린다. 구간을 나누는 규칙은 `walkRoute.ts`의 `createRouteBuilder`(간격 15초 초과, 정확도 20m 초과 또는 없음, 속도 5m/s 초과, 순번 불연속, 시각이 늘지 않음)를 SVG 지도(6-2)와 같이 쓴다. 구간마다 선이 따로라 끊긴 곳은 이어지지 않는다. 새 좌표는 마지막 선 뒤에 점만 이어 붙이고(약 1초 간격으로 모아 보냄) 끊김 뒤에만 새 선을 만든다. 선 색은 `colors.deepOrange`, 두께 6, 단색이다. 카카오 Polyline은 끝 모양(둥근 끝)을 설정하는 옵션이 없어 지도의 기본 모양을 따른다.
- 앱을 다시 열었을 때: 트래커가 서버의 진행 중 산책을 이어 받을 때 `GET /walks/{id}`의 좌표와 마커를 불러와 다시 그린다(좌표는 서버가 받은 것까지만이고, 보내지 못한 큐는 앱이 종료되면 사라진다).
- 5-1 마커: 앱에서 마커 버튼을 누르면 위치를 알 때 바로(저장 중 반투명) 지도에 올라가고, 저장되면 불투명해지고, 실패하면 빠진다. 결과를 모르는 실패(네트워크, 시간 초과)는 같은 항목을 다시 누를 때까지 남는다. 서버 응답에는 `client_marker_id`가 없어서 중복은 서버 id(저장이 끝난 마커)와 종류+위치(저장 중인 마커)로 거른다. 종류별 아이콘: 냄새, 배변, 다른 개, 포토스팟(OTHER + 메모 "포토스팟"), 그 밖은 위치 아이콘. 아이콘은 `src/assets/icons`의 SVG path를 `kakaoMarkerIcons.ts`로 옮겨 WebView 안에서 그린다(오프라인).
- 카메라 따라가기: 처음 위치에서 레벨 3으로 맞추고 이후에는 `panTo`만 한다. 지도를 끌거나 두 손가락으로 확대·축소하면 따라가기가 풀리고 "내 위치로" 버튼이 나온다. 누르면 다시 따라간다.
- 6-2 저장된 경로: 같은 컴포넌트를 읽기 전용으로 써서 저장된 구간과 마커를 그리고 경로 전체가 들어오게 맞춘다(내 위치, 따라가기 없음). 새 API 호출은 없다(화면이 이미 읽는 `loadWalkRoute`, 요약 마커를 쓴다). 좌표가 2개 미만이면 "기록된 이동 경로가 없어요"를 보여 준다. 9-2(기록 상세)에는 지도 영역이 없어서 바꾸지 않았다.
- 견고함: WebView가 다시 열리면(프로세스 종료 뒤 reload) `ready`마다 전체 상태(구간과 마커)를 한 번 다시 보낸다. WebView에서 오는 메시지는 모양을 확인하고 모르는 종류는 무시한다. 로그에는 좌표, 토큰, 키를 남기지 않는다.

### 미확인 (phone) 실험 순서
GPS 좌표는 실제로 움직여야 바뀐다(좌표는 약 10초마다 기록). 실내에서 서서 확인할 수 있는 것과 걸어야 하는 것을 나눈다.

서서 확인(실내 가능):
1. `.env.local`에 `EXPO_PUBLIC_WALK_MAP_KAKAO_WEB=true`, 서버를 `npx expo start -c`로 다시 시작, 산책을 시작해 5-1로 간다.
2. 내 위치 마커가 보이고 지도가 내 위치 가운데에 레벨 3 정도로 맞는지.
3. 지도를 한 손가락으로 끌어 본다 → 따라가기가 풀리고 오른쪽 위에 "내 위치로"가 나오는지. 누르면 내 위치로 돌아오고 버튼이 사라지는지. 두 손가락 확대·축소도 같은지.
4. 플러스 버튼 → "냄새 맡기"를 누르면 내 위치에 반투명 아이콘이 바로 나타나고 곧 불투명해지는지. 배변, 다른 개, 포토스팟도 모양이 서로 다른지.
5. 같은 마커를 연달아 눌러 겹쳐 쌓이지 않는지(한 번 누를 때마다 하나).
6. 와이파이와 데이터를 끄고 마커를 누르면 오류 안내가 뜨고, 결과를 모르는 실패라서 반투명 마커가 남아 있는지. 네트워크를 켜고 같은 항목을 다시 누르면 하나로 저장되어 불투명해지는지(확실한 실패, 예: 서버 거절일 때만 마커가 지도에서 빠진다).
7. 앱을 완전히 종료했다가 다시 열어 5-1로 돌아오면 저장된 마커가 다시 그려지는지.

걸어서 확인(바깥, 최소 3~4분, 약 30분 이내):
8. 걷기 시작하면 약 10~20초 뒤부터 주황색 선이 내 위치 뒤로 늘어나는지, 카메라가 따라오는지.
9. 일시정지 후 다시 시작하거나 신호가 끊겼다 돌아오면 선이 이어지지 않고 끊겨 새 선이 시작되는지(직선으로 건너뛰지 않음).
10. 걷는 중 앱을 종료했다가 다시 열면 이미 기록된 선이 다시 그려지는지.
11. 산책을 끝내고 6-2에서 저장된 경로와 마커가 지도에 그려지고 경로 전체가 보이도록 맞는지. 좌표가 거의 없는 산책(서서 끝냄)은 "기록된 이동 경로가 없어요"가 나오는지.
12. `EXPO_PUBLIC_WALK_MAP_KAKAO_WEB`를 지우거나 키를 잘못 넣으면 5-1, 6-2가 기존 자리 표시 지도와 안내로 돌아오는지.

## shelter-web (보호소 웹) 로그인, 세션, 로그아웃 (연동 1~4단계)

### 구현함, 브라우저에서 미확인
- `npm run build`(tsc, vite build)와 개발 서버가 `http://localhost:3000`에서 뜨는 것(HTTP 200)만 확인했다. 로그인과 API 호출은 브라우저에서 실행하지 않았다.
- 포트: BE의 CORS가 `http://localhost:3000`, `http://127.0.0.1:3000`만 허용한다(BE에 고정). Vite를 `localhost:3000`, `strictPort`로 고정했고 프록시는 없다. 3000이 사용 중이면 실행이 실패한다(다른 포트로 넘어가지 않음). 주소창도 `localhost`로 연다(LAN IP 불가).
- API 클라이언트(`shelter-web/src/api/client.ts`): 앱 것을 복사. 10초 타임아웃, JSON이 아닌 2xx는 `INVALID_RESPONSE`, 오류 정규화(`{code,data,message}`, `{detail: 문자열|객체|배열}`). 401은 주입된 핸들러가 처리한다. Base URL은 `VITE_API_BASE_URL`(`.env.example`의 기본값 `http://localhost:8000`, 실제 값은 git에서 제외되는 `.env.local`).
- 토큰: `sessionStorage`(탭을 닫으면 사라짐)와 메모리. `localStorage`는 쓰지 않고 로그에 남기지 않는다.
- 로그인: `POST /auth/login` → `GET /users/me`(role을 대문자로 정규화) → role `SHELTER`이고 `shelter_id`가 있을 때만 `#dashboard`. 그 밖의 role(ADMIN, USER 포함)이나 `shelter_id`가 null이면 `POST /auth/logout` 한 번, 토큰 삭제, 안내 문구.
- 오류 문구: 401 아이디 또는 비밀번호, 429 대기 초(본문 `data.retry_after_seconds`), 네트워크/CORS "서버에 연결할 수 없어요", 409 잠금 충돌(자동 재시도 없음).
- 세션 가드: `#login`과 `#verification`(로그인 화면의 안내 링크) 외의 모든 경로는 세션이 필요하다. 처음 열 때 `/users/me`를 한 번만 확인한다. 어디서든 401이면 토큰을 지우고 `#login`으로 가며 "다시 로그인해 주세요."를 보여 준다.
- 로그아웃: 상단 "로그아웃". `POST /auth/logout`을 한 번만 부르고(재시도 없음), 실패해도 토큰을 지우고 `#login`으로 간다.
- 개발용 미리보기 버튼: `npm run dev`에서 `VITE_ALLOW_DEMO_PREVIEW=true`일 때만 보인다. 빌드에는 나오지 않는다.
- 강아지, 일정, 예약, 신고, 이력, 설정 화면은 아직 `DemoContext`의 예시 데이터다(10단계에서 교체). "목업 미리보기" 배너도 그대로다.

### 실행
```
cd shelter-web
npm install
copy .env.example .env.local   (필요하면 VITE_API_BASE_URL 수정)
npm run dev                     → http://localhost:3000
```
BE는 `http://localhost:8000`에서 떠 있어야 한다.

### 수동 테스트 (브라우저, 로컬 BE)
비밀번호는 직접 입력한다. 문서와 로그에 적지 않는다.
1. `http://localhost:3000`을 연다 → 로그인 화면. 개발자 도구 Network에서 `localhost:8000` 호출이 CORS 오류 없이 되는지 본다.
2. `shelter01`로 로그인 → `#dashboard`. Network에 `/auth/login`, `/users/me`가 순서대로 있다.
3. 새로고침(F5) → 로그인 화면을 거치지 않고 대시보드가 유지된다. 주소를 `#dogs`로 직접 바꿔도 열린다.
4. 탭을 닫고 새 탭에서 열기 → 로그인 화면(sessionStorage는 탭마다다).
5. 틀린 비밀번호 → "아이디 또는 비밀번호가 맞지 않아요." 비밀번호 칸이 비워진다.
6. 10번 넘게 연속 실패 → "N초 뒤에 다시 시도해 주세요."(N은 서버가 준 값).
7. 일반 사용자 계정으로 로그인 → 보호소 계정 전용 안내가 나오고 대시보드로 가지 않는다. Network에 `/auth/logout`이 한 번이다. 개발자 도구 Application → Session Storage에 토큰이 남아 있지 않다.
8. (가능하면) `shelter_id`가 없는 SHELTER 계정 → 담당 보호소 미연결 안내.
9. 로그인한 뒤 Session Storage의 `shelter_access_token`을 지우거나 값을 바꾸고 다른 화면으로 이동/새로고침 → `#login`과 "다시 로그인해 주세요."
10. 로그아웃 클릭 → `#login`. Network에 `/auth/logout`이 한 번이고, 뒤로 가기로 대시보드에 가면 다시 로그인 화면이다.
11. BE를 끄고 로그인 → "서버에 연결할 수 없어요."
12. 로그아웃 요청이 실패해도(BE 종료 후 클릭) 로그인 화면으로 돌아가는지.

## 개발용 가짜 GPS (`EXPO_PUBLIC_DEV_FAKE_GPS=true`, `__DEV__`일 때만)

구현했고 타입 검사를 통과했다. 시뮬레이션(가짜 시계)으로 표본 간격 3~5초, 속도 최대 1.87m/s, 정확도 4~12m, 시각이 늘기만 하는지를 확인했다. 기기에서는 아직 확인하지 않았다(NOT VERIFIED).
기록(트래커)과 5-1 지도 마커는 `locationSource.ts`라는 같은 창구에서 위치를 받는다. 가짜일 때는 같은 표본이 둘에게 동시에 가고, 일시정지, 신호 끊김, 경로 끊김 규칙은 실제 데이터와 같은 코드를 지난다. 표본 시각은 내보내는 순간의 실제 현재 시각이다.

### 확인할 수 있는 것 (집에서)
- 경로 선이 그려지고 늘어나는지, 카메라 따라가기와 "내 위치로" 버튼
- 앱의 마커 버튼으로 찍은 마커가 지도에 올라오고 서버에 저장되는지
- 좌표가 BE에 저장되는지(409 없이 보내지는지), 종료 후 6-2의 저장된 경로와 마커
- 일시정지/재개, 앱 재시작 뒤 경로 복구
- `EXPO_PUBLIC_DEV_FAKE_GPS_GAP=true`: 1분마다 20초 표본이 없어 경로가 끊기는지. `EXPO_PUBLIC_DEV_FAKE_GPS_BAD_ACCURACY=true`: 약 7번째마다 30m 표본이 나와 그 앞뒤가 이어지지 않는지

### 확인할 수 없는 것 (계속 NOT VERIFIED)
- 실제 GPS의 정확도와 신호 품질
- 화면 잠금, 백그라운드 수집(앱은 foreground 전용)
- 실제 위치 권한 요청/거부 흐름(가짜일 때는 권한을 묻지 않고 허용으로 본다)
- 실제 이동 속도와 위치 튐

### 5단계 보호소 프로필, 지역 (구현함, 브라우저에서 미확인)
- `GET /shelters/{shelter_id}`(`shelter_id`는 `/users/me`의 값)로 대시보드 제목(이름, 주소)과 설정 화면을 채운다. 대시보드는 이 호출이 실패해도 나머지를 그대로 보여 준다.
- 설정: 이름, 연락처, 주소, 웹사이트는 읽기 전용이다(수정 API 없음). "목업 초기화" 버튼은 없앴다.
- 지역 변경: `GET /regions/sido` → `GET /regions/sigungu?sido_code=` 선택 → `PATCH /shelters/{id}/region`. 422는 "선택할 수 없는 지역", 그 밖의 실패는 공통 문구(409는 재시도 안내, 자동 재시도 없음).
- 현재 지역은 응답에 `region_name`이 없어 처음에는 "지역 코드 N"으로 보이고, 저장하면 이름으로 바뀐다.
- 개발용 미리보기(로그인 없음)에서는 서버 데이터를 불러오지 않는다.

수동 테스트:
1. `shelter01`로 로그인 → 대시보드 제목에 보호소 이름과 주소가 나온다(Network에 `GET /shelters/{id}`).
2. 설정 → 정보 4개가 읽기 전용으로 보이고 안내 문구가 있다.
3. 시도 선택 → 시군구 목록이 바뀐다 → 선택 후 "지역 저장" → 현재 지역이 이름으로 바뀐다. 새로고침 후에도 지역 코드가 바뀐 값이다.
4. BE를 끄고 설정을 열면 오류와 "다시 불러오기" 버튼이 보인다.

### 6단계 강아지 (구현함, 브라우저에서 미확인)
- 목록: `GET /shelters/{id}/dogs`와 `?walkable=true`를 함께 불러 "산책 가능/산책 중지"를 표시한다(목록 응답에 산책 설정이 없어서). 사진은 `/media/...` 상대 경로 앞에 API 주소를 붙이고, 없으면 "사진 없음".
- 산책 가능 전환: `PATCH /dogs/{id}/walk-settings {walkable}` 후 목록을 다시 불러온다. "등록 일시 중지" 대신 쓴다.
- 등록: `POST /dogs/walk-registration`(multipart, 원본 File, Content-Type 직접 지정 없음). 필드: 이름, 견종, 나이, 개월(0~11), 경험 수준(BEGINNER/INTERMEDIATE/EXPERIENCED), 크기(SMALL/MEDIUM/LARGE), 난이도 점수(1~5, 0.5 단위), 최대 산책 시간(30/60/90), 주의사항, `shelter_id`, `slots`(JSON 문자열, 한국 시간, 1개 이상), 사진(필수). 422는 입력칸별 문구, 409는 BE 문장(없으면 일정 겹침 안내).
- 수정: 이름, 견종, 나이는 `PUT /dogs/{id}/traits`(서버가 준 성별, 몸무게, 특이사항, 설명은 함께 보내 지워지지 않게 함). 크기, 경험 수준, 난이도 점수, 최대 산책 시간, 주의사항은 `PATCH /dogs/{id}/walk-settings`(바뀐 칸만). 사진은 수정 API가 없어 읽기 전용이다.
- 삭제 API가 없어 삭제 버튼은 없고, 안내 문구만 둔다.
- **BE 응답 모양 가정**: `GET /dogs/{id}`가 설정을 `walk_settings` 안에(없으면 최상위에) 주고 `weight`, `special_note`, `description`을 최상위에 둔다고 가정했다. 실제와 다르면 수정 화면의 초기값이 비어 보인다.

수동 테스트:
1. 강아지 → 목록과 사진이 나온다(사진 주소가 `localhost:8000/media/...`).
2. "산책 가능으로 전환/해제"를 누르면 배지가 바뀐다.
3. 강아지 등록: 사진 없이 → "사진을 선택해 주세요". 난이도 점수 3.3 → 칸 오류. 사진, 일정 한 줄을 넣고 등록 → 목록에 보인다. Network에서 요청이 multipart(boundary 포함)인지 본다.
4. 이미 있는 시간과 겹치게 일정을 넣어 등록 → 409 문구.
5. 정보 수정: 이름만 바꿔 저장 → 목록에 반영. 아무것도 안 바꾸고 저장 → "바뀐 내용이 없어요."
6. 다른 보호소 강아지 id로 `#dogs/edit/숫자` 직접 이동 → 403 문구(가능하면).

### 7단계 산책 일정 (구현함, 브라우저에서 미확인)
- 목록: 보호소 전체 일정 API가 없어서 `GET /shelters/{id}/dogs` 뒤에 강아지별 `GET /dogs/{id}/date-slots`를 3개씩 동시에 부른다. 기본은 활성 일정만 보이고 "종료된 일정도 보기"로 비활성도 본다. 일부 강아지만 실패하면 나머지는 보이고 실패한 강아지 이름을 안내한다.
- 등록: `POST /dogs/{id}/date-slots`에 일정 배열(1개 이상)을 보낸다. 산책 시간은 30/60/90 선택이고 종료 시간은 시작 + 산책 시간으로 자동 계산한다(자정을 넘으면 막음). 한국 시간, 시간대 표기 없음. 과거 날짜와 겹침은 BE가 검증하고 422/409 문장을 그대로 보여 준다.
- 종료: `DELETE /dogs/{id}/date-slots/{slot_id}`(204). 확인 창에 "다시 열 수 없다"를 적었다. 409면 진행 중인 예약이 있으니 예약을 먼저 취소하라고 안내한다. 성공과 실패 모두 목록을 다시 불러온다.
- 일시 중지/재개 UI는 없앴다(API 없음). 일정 수정(PATCH)은 화면에 맞는 자리가 없어서 넣지 않았다.
- **BE 응답 모양 가정**: 일정 항목이 `id`(또는 `date_slot_id`), `slot_date`, `start_time`, `end_time`, `duration_minutes`, `is_active`를 준다고 가정했다. 한국 시간 필드가 없으면 `starts_at`, `ends_at`(UTC)을 한국 시간으로 바꿔 쓴다. 실제와 다르면 목록이 비어 보이거나 시간이 비어 보인다.

수동 테스트:
1. 일정 → 등록한 강아지들의 활성 일정이 날짜순으로 보인다. 다른 강아지가 없는 보호소면 빈 목록.
2. 일정 등록: 강아지 선택, 내일 날짜, 10:00, 60분 → "종료 11:00" 표시 → 등록 → 목록에 보인다.
3. 같은 시간으로 다시 등록 → BE의 겹침 문구. 어제 날짜로 등록 → BE의 과거 날짜 문구.
4. 줄 추가로 두 일정을 한 번에 등록 → 둘 다 보인다.
5. "일정 종료" → 확인 창 → 목록에서 사라지고 "종료된 일정도 보기"에서 "종료됨"으로 보인다.
6. 승인된 예약이 걸린 일정을 종료 → "진행 중인 예약이 있어요" 안내(가능하면).
7. 종료한 일정에는 종료 버튼이 없다.

### 8단계 예약 목록과 상세 (구현함, 브라우저에서 미확인)
- 목록: `GET /shelters/{id}/walk-requests?status=&limit=20&offset=`. 탭은 승인 대기 / 승인됨 / 거절됨 / 취소됨이다. 응답에 total과 has_more가 없어서 한 번에 가져온 개수가 20보다 적으면 "더 보기"를 숨긴다(최신순, 중복 id는 제거). 항목의 라벨은 `display_status`(산책 완료 포함)를 쓴다. 시각은 UTC를 한국 시간으로 바꿔 보여 준다. 승인됨 탭은 끝난 산책이 빠진 목록이다.
- 상세: `GET /walk-requests/{id}`를 행을 열 때만 부른다. 강아지, 신청자 별명과 경험 항목(반려견 경험, 경험한 견종, 산책 빈도), 일정, 상태, 거절 사유, 취소 정보를 보여 준다. 신청자 이름과 나이는 보호소에게 항상 null이라 보여 주지 않는다.
- 이 단계의 승인과 거절 버튼은 비활성 자리표시자다(다음 단계에서 연결). 대시보드의 예시 신청 카드는 "예약 관리" 목록으로만 연결한다.
- **BE 응답 모양 가정**: 경험 항목(`dog_experience` 등)의 값 형식(코드인지 문장인지)을 모른다. 값을 그대로(불리언은 있음/없음) 보여 준다. 코드가 오면 그대로 보이므로 확인이 필요하다.

수동 테스트(앱에서 신청을 하나 만들어 둔다):
1. 예약 관리 → "승인 대기" 탭에 신청이 보이고, 시각이 한국 시간이다.
2. 다른 탭(승인됨, 거절됨, 취소됨)을 눌러 목록이 바뀌고 빈 탭은 "이 상태의 신청이 없어요."가 나온다.
3. "상세 보기" → 신청자 별명, 경험 항목이 보이고 이름과 나이는 없다. 승인, 거절 버튼은 비활성이다.
4. 상세에서 뒤로 가면 보던 탭이 유지된다.
5. 신청이 20개를 넘으면 "더 보기"가 나오고 누르면 이어진다(가능하면).
6. BE를 끄고 탭을 누르면 오류와 "다시 불러오기"가 나온다.

### 9단계 승인, 거절, 보호소 코드 발급, 대시보드 (구현함, 브라우저에서 미확인)
- 승인: 확인 창 후 `PATCH /walk-requests/{id} {action:"APPROVE"}`. 거절: 사유 코드(일정이 맞지 않아요 / 경험이 맞지 않아요 / 정보가 부족해요 / 기타)와 선택 사유. 기타는 사유가 비어 있으면 보내지 않고 안내한다. 본문에는 허용된 필드만 넣는다. 성공하면 상세를 다시 불러오고 새 상태에 맞는 문구("신청을 승인했어요." 등)를 보여 준다.
- 409: 신청을 다시 조회해서 상태가 바뀌었으면 "이미 처리된 신청이에요. 최신 상태를 불러왔어요."(문구 비교 없음), 그대로면 BE의 문장 또는 재시도 안내를 보여 준다. 자동 재시도 없음.
- 예약 취소(보호소): 상세 화면에 맞는 자리가 있어서 넣었다. 승인됨이고 산책 기록이 없고 시작 전일 때만 "예약 취소"가 보이고, 사유(보호소 일정이 바뀌었어요 / 방문을 받기 어려워요)를 고른다. 대기 중 신청은 "거절"로 처리한다.
- 보호소 코드: 승인됨이고 산책 기록이 없는 신청에 패널이 보인다. 예약 시작~종료 안에서만 버튼이 켜지고(브라우저 시계 기준, 최종 판단은 서버) 밖이면 이유를 적는다. `POST /walk-requests/{id}/shelter-code`(본문 없음). 코드는 큰 글씨로 앞자리 0을 유지해 보여 주고, 한국 시간 만료 시각과 남은 시간을 보여 주며, 만료되면 코드를 지운다. "숨기기"가 있다. 이미 발급했거나 화면에 보이면 다시 발급 전에 "이전 코드는 쓸 수 없게 돼요" 확인을 한다. 코드는 그 컴포넌트의 상태에만 있고, 저장소, 주소, 로그, 다른 상태에 넣지 않는다(다른 화면으로 가거나 새로고침하면 사라짐). 409 WALK_REQUEST_NOT_ELIGIBLE, 409 WALK_REQUEST_RETRYABLE(한 번 더 누르라고 안내), 403, 404, 500(서버 설정 문제)은 쉬운 말로 안내한다.
- 대시보드: 승인 대기 수는 `status=PENDING`을 limit=100씩 마지막 쪽까지 넘기며 센다(상한 50쪽). 카드는 최신 5건(강아지, 일정, 상세 링크)이다. 실패하면 이 부분만 오류와 "다시 불러오기"가 보인다. "확인할 신고"와 산책 현황은 아직 예시다.
- 연결된 화면(강아지, 일정, 예약, 설정)은 "목업 미리보기" 안내와 DEMO 표시를 뺐다. 데모 데이터에서 강아지, 일정, 예약은 지웠다(신고와 산책 이력만 남음).
- 신청자 표시가 별명과 경험 항목뿐이라 대시보드 카드에는 신청자가 없다(목록 응답에 신청자 정보가 없음).

수동 테스트(앱에서 신청을 하나 만들고, 보호소에서 일정 시간이 지금 포함되도록 등록해 둔다):
1. 대시보드: 승인 대기 건수와 카드가 실제 신청과 맞는다. 카드의 "신청 확인하기"로 상세에 간다.
2. 상세에서 "거절" → 기타 선택, 사유 비움 → "사유를 적어 주세요". 사유를 적고 거절 → "신청을 거절했어요." 상태가 거절됨, 거절 사유가 보인다. 앱에서도 거절로 보인다.
3. 다른 신청을 "승인" → 확인 → "신청을 승인했어요." 상태가 승인됨.
4. 승인됨 상세에서 예약 시간이 지금을 포함하면 "코드 발급"이 켜지고, 포함하지 않으면 꺼져 있고 이유가 보인다(시간 밖에서 눌러지지 않음).
5. 코드 발급 → 6자리가 크게 보이고(앞자리 0이 있으면 유지), 남은 시간이 줄어든다. "숨기기"로 사라진다. 다시 발급하면 확인 창이 뜬다. 앱의 4-1 코드 입력에 넣어 보고, 이전 코드는 거절되는지 본다.
6. 새로고침하면 코드가 사라진다. 개발자 도구 Application에서 localStorage, sessionStorage에 코드가 없는지 본다(토큰 항목만 있음).
7. 이미 처리된 신청을 두 탭에서 동시에 승인 → 두 번째는 "이미 처리된 신청이에요."
8. 시작 전의 승인 예약에서 "예약 취소" → 사유 선택 → 취소됨 탭으로 이동한다.
