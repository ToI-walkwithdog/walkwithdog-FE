# 검증 현황

단계마다 갱신한다. "확인"은 실제 기기에서 인증된 API 호출로 본 것이고, "미확인"은 아직 보지 못한 것이다.
예약 상태는 DB를 직접 바꾸지 않고 보호소 테스트 계정과 승인 API로 만든다.

## 테스트 환경 (2026-11-25)
- 로컬 BE(`walkwithdog-BE`, dev 브랜치)와 로컬 PostgreSQL
- 주의: 지금까지의 테스트 산책은 예약 3번의 산책 1번뿐이고 11초(09:02:24~09:02:35 UTC)였다. 짧은 산책으로는 정지·마커·신고·좌표 전송을 확인할 수 없다.
- 다음 테스트 산책(레벨업 횟수를 채우는 산책)은 2~3분 걷고, 7단계 "미확인(더 긴 테스트 산책이 필요함)" 항목을 함께 확인한다.
- 실제 기기에서 Expo Go로 FE 실행
- 보호소 계정 `shelter01`을 Swagger에서 사용해 일정 생성, 예약 승인, 보호소 코드 발급
- 예약 3번(승인 상태)으로 보호소 코드부터 산책 종료까지 진행

## 6단계 내 예약, 취소 (8-1~8-8)

### 기기에서 확인함
- 내 예약 목록 불러오기와 "승인 대기" 카드 표시(시각은 KST)
- 대기 중인 예약 취소 흐름(8-4 → 8-7 → BottomSheet 확인 → 8-8)
- 취소 뒤 목록의 "지난 예약" 탭 반영
- 이미 취소된 예약의 안내 문구(409 `REQUEST_ALREADY_CANCELLED`)
- 승인 상태 상세 화면(8-3)

### 미확인
- 취소 오류 경로: `CANCEL_TIME_EXPIRED`, `WALK_RECORD_EXISTS`, `REQUEST_STATE_CONFLICT`, `REQUEST_LOCK_CONFLICT`
  (`REQUEST_ALREADY_CANCELLED`는 API 재전송으로 따로 확인한다)
- 한 페이지(20건)를 넘는 목록: 더보기, offset을 원본 개수만큼 더하는 동작, 예약 ID 중복 제거
- 승인 뒤 취소
- 403과 404 처리: HTTP 상태로만 나눈다. 나이 확인 대기 계정은 `GET /users/me`의 단계로 판단한다.
- 확정 탭에 산책을 마친 예약이 "산책 완료"로 보이는지
- 예약 취소 뒤 목록 캐시 무효화: 취소 뒤 뒤로 돌아간 목록이 첫 페이지부터 다시 불러와지는지

## 7단계 보호소 코드, 시작, 산책 중, 신고, 종료 (4-x, 5-x)

### 기기에서 확인함
테스트 산책(예약 3번, 산책 1번)은 09:02:24~09:02:35 UTC, 즉 11초였다. 11초 안에 할 수 있는 것만 확인으로 둔다.
- 보호소 코드 입력(4-1)과 산책 시작(체크리스트 4-4 → 5-1)
- 위치 권한 요청과 허용
- 산책 시간이 계속 늘어남
- 산책 종료와 6-1로 이동

### 미확인 (더 긴 테스트 산책이 필요함)
이전에 확인으로 적었으나 11초 산책으로는 해 볼 수 없어 되돌렸다. 다음 테스트 산책은 2~3분 걷고 아래를 모두 포함한다.
- 일시정지와 이어 걷기: 정지 중에도 시간이 계속 늘고 "일시정지됨"만 표시되는지, 이어 걷기가 되는지
- 정지 중에 신고 시트와 마커 메뉴를 열고 닫아도 정지 상태가 바뀌지 않는지
- 마커 4종 저장: 냄새 맡기, 배변, 다른 개, 포토스팟(`OTHER` + 메모 "포토스팟")
- 비행기 모드 뒤 같은 마커 재시도에서 중복 저장되지 않는지
- 신고 전송과 결과 화면(5-6, 5-7)
- 화면 잠금 뒤 돌아오기
- 앱을 완전히 종료한 뒤 홈에서 진행 중인 산책 복구
- 6-2에 실제 경로(폴리라인)와 마커가 그려지는지(좌표가 쌓일 만큼 걸어야 한다)

### 미확인 (그 밖)
- 자동 종료(`AUTO_TIMEOUT`)와 그 뒤의 복구 경로(안내 문구, 6-1 이동, 보내지 못한 좌표 안내, 종료 뒤 좌표 전송 차단)
- 기기 시계가 서버보다 앞서거나 뒤일 때의 좌표 전송과 마커, 신고 전송
- 종료 응답이 유실됐을 때 같은 산책의 상세로 확인하는지
- 산책 중 세션 만료와 다시 로그인 뒤 같은 산책으로 돌아오기
- 1시간을 넘기는 일시정지(정지 중에는 좌표가 없어 서버가 자동 종료한다)
- 오래 오프라인으로 걷는 경우(메모리 큐, 순번 연속 유지, 앱 종료 시 큐 유실)
- 보호소 코드 5회 실패 잠금(429 `SHELTER_CODE_RATE_LIMITED`)
- 위의 6단계 미확인 중 "한 페이지를 넘는 목록", "취소 오류 경로"
- 이번 기기 테스트에서 따로 기록하지 않은 항목: 틀린 코드(422)와 만료 코드, 위치 권한 거부, GPS 끊김 자동 안내(30초 무신호)와
  위치 다시 연결, 신고 실패 뒤 "다시 전송하기", `DUPLICATE_RECENT` 확인, 위치가 없는 마커(`MARKER_LOCATION_UNAVAILABLE`),
  좌표 순번과 재전송 동작, 정지와 재개 사이 간격이 선으로 이어지지 않는지

### 알려진 한계
- 앱이 foreground일 때만 위치를 모은다. 백그라운드에서는 수집이 끊기고 서버가 새 좌표 없이 1시간이 지나면 자동 종료한다.
- 보내지 못한 좌표 큐는 메모리에만 있다. 앱 프로세스가 종료되면 사라진다(저장소 도입 여부는 별도 결정).
- 지도는 목업 그림이고 실제 경로는 그리지 않는다. 6-x 이후 화면은 목업이다(8단계). 종료 결과는 `getEndedWalk()`에 남는다.

### 기기 시계와 좌표 시각
좌표의 `recorded_at`은 기기가 위치를 얻은 실제 시각 그대로 보낸다. 서버는 시작 이후, 서버 현재 시각 이하만 받고
위반하면 batch 전체를 409로 거절한다. 기기가 앞서면 서버 시각이 그 시각을 지날 때까지 큐에 두고, 뒤면
시작 이전 관측은 보내지 않는다. 서버 시각은 `GET /walks/active`의 `elapsed_seconds`로 추정하고 5분마다 다시 맞춘다.
이 처리는 아직 기기에서 확인하지 않았다.

## 8단계 인계, 기록 저장, 레벨업, 이력 (6-1~6-3, 9-1, 9-2)

구현했고 타입 검사만 통과했다. 기기에서는 아직 아무것도 확인하지 않았다.
테스트 데이터: 예약 3번의 산책(종료됨, 인계 전)으로 인계, 메모, 이력을 확인한다.

### 기기에서 확인함
- 없음

### 미확인
- 6-1 정상 인계: 세 항목을 체크하고 접수(201), 접수 뒤 6-2로 이동
- 6-1 같은 내용 재전송이 200으로 이어지는지(응답 유실 뒤 같은 본문으로 다시 누르기), 다른 내용을 보내면 409 처리
- 6-1 "인계에 문제가 있어요" 접수(문제 내용 1~500자, 미완료 항목이 하나 이상 있어야 함)
- 6-1 자동 종료(`AUTO_TIMEOUT`) 산책의 확인 안내와 `acknowledge_auto_timeout` 전송
- 6-1 중단된 산책(문제 접수만 가능한 화면)
- 6-2 서버 확정 통계(총 시간, 거리, 평균 속도)와 날짜(KST), 실제 경로 폴리라인과 마커 표시
- 6-2 경로가 끊기는지: 정지·재개 사이(15초 초과), 정확도가 나쁜 좌표(20m 초과나 없음), 비정상 속도(5m/s 초과), 페이지(500개) 경계. 좌표가 없는 산책에서 자리 표시 지도만 나오는지
- 6-2 메모 저장(최초 201, 수정 200), 같은 메모 재저장, 메모 버전 충돌(409), 빈 메모는 저장하지 않음
- 6-2 메모 규칙: 인계 전(NOT_CONFIRMED)이면 막고 인계 안내, 첫 저장은 expected_version=0, 수정은 서버 버전, 응답 유실이나 409 뒤에 서버 메모를 보여 주고 선택하게 하는지(조용히 덮어쓰지 않는다)
- 6-2 메모는 선택: 메모 없이 저장해도 레벨 평가로 넘어가는지, 인계가 필요 없는 산책(NOT_REQUIRED)은 인계 버튼 없이 메모만 되는지
- 6-2 저장 뒤 레벨 평가 확인(3초 간격, 약 60초): PENDING은 "레벨을 평가하는 중", FAILED는 "지연", 끝내 끝나지 않으면 이력으로 이동하고 나중에 다시 확인
- 6-3 레벨업 화면과 서버 레벨 표시(BE `.env`에 레벨 정책 변수를 넣은 뒤)
- 9-1 서버 이력 목록, 통계 카드(`history_walk_count`, `history_distance_m`, 거리 일부 미확인 표시), 빈 목록, 오류와 다시 시도, 당겨서 새로고침
- 9-1 한 페이지(20건)를 넘는 목록과 더보기(마지막 페이지 판단에 서버 `total`도 함께 사용), 인계·메모 저장 뒤 목록 새로고침
- 9-1 "인계 필요" 필터: 인계 전 산책 수(서버 `total`), 항목을 누르면 6-1이 열리는지
- 9-1을 다시 볼 때 평가가 끝나지 않았던 산책의 레벨 결과를 다시 확인하는지
- 같은 레벨업을 다시 보여 주지 않는지(계정 ID와 이벤트 ID를 `expo-secure-store`에 기억), 앱 재시작 뒤에도 유지되는지
- 6-3 문구("꾸준한 산책으로 새로운 레벨을 달성했어요.")와 서버 레벨 숫자(`after_level`)
- 9-2 상세(메모, 기록한 항목 개수, 인계 상태), 인계 전 산책의 "인계 확인하기"
- 자동 종료와 직원 중단 산책에서 레벨업이 나오지 않는지

### 레벨업 로컬 테스트 계획
레벨은 성취 지표일 뿐이며 예약 권한, 강아지 크기, 난이도와 무관하다.

- **사전 설정(걷기 전에 해야 한다):** 로컬 BE `.env`에 `VOLUNTEER_LEVEL_POLICY_VERSION`과 `VOLUNTEER_LEVEL_POLICY_START_AT`(UTC)을
  넣고 BE를 재시작한 뒤에 산책을 시작한다. 현재 값은 `local-level-v1`, `2026-11-25T00:00:00+00:00`이다.
- **반영되는 산책:** 정책 시작 이후에 시작했고, `COMPLETED`이며, 종료 사유가 `USER`이고, 인계가 `SELF_REPORTED`(정상 인계)이며,
  같은 계정의 산책이다. 최소 시간, 거리, 좌표 수 조건은 없다. 같은 산책은 두 번 반영되지 않는다.
- **제외되는 산책:** 자동 종료(`AUTO_TIMEOUT`), 직원 중단, 정책 시작 이전 산책, 문제 접수(`ISSUE_REPORTED`) 인계.
  문제 접수로 낸 인계는 나중에 반영 대상으로 바꿀 수 없다.
- **레벨 기준(반영 산책 수, 평가 중인 산책 포함, 줄지 않는다):** Lv.1 = 0~2, Lv.2 = 3~9, Lv.3 = 10~19, Lv.4 = 20~39, Lv.5 = 40 이상.
- **레벨 2까지의 산책 수:** 정상 인계를 마친 산책 3번. 예약 3번의 산책이 1번째이고 2번 더 걷는다.
  각 산책마다 일정 만들기, 신청, 승인, 코드 발급(`shelter01`)을 반복하고, 인계는 반드시 세 항목을 모두 체크한 정상 인계로 한다.
- **기대 결과:**
  - 1번째와 2번째 산책: 인계 뒤 6-2 저장 때 평가가 `PENDING`을 거쳐 `COMPLETED`(레벨업 없음)가 되고 6-3은 열리지 않는다.
  - 3번째 산책: `COMPLETED` + `level_up_event`가 오고 6-3에 "산책 레벨 2"가 나온다. 9-1을 다시 열거나 앱을 다시 시작해도 같은 6-3이 또 나오지 않는다.
  - 평가 작업은 30초마다 돌아 몇 초에서 수십 초 걸린다. 약 60초 안에 끝나지 않으면 이력으로 넘어가고 9-1을 다시 볼 때 결과를 확인한다.
- **제외 확인(선택, 산책 3번 더):** 자동 종료 산책(`AUTO_END_AFTER_SECONDS`를 짧게), 직원 중단 또는 문제 접수 인계 산책에서 레벨업이 나오지 않는지.
- **총 필요한 산책:** 레벨 2 확인 3번. 제외 확인까지 하면 최대 6번.

## 통계 필드 매핑 (확정)
`GET /volunteers/me`의 `history_*`(종료한 모든 산책 = COMPLETED + INTERRUPTED, 자동 종료 포함)를 9-1과 10-1 모두에 쓴다.
9-1 목록과 같은 범위라 숫자를 목록과 맞춰 볼 수 있다. 9단계(10-1 마이페이지)도 같은 필드를 쓴다.

| 숫자 | 필드 | 비고 |
|---|---|---|
| 총 산책 | `history_walk_count` | 9-1 카드, 10-1 카드 |
| 총 거리 | `history_distance_m` | `history_distance_is_complete`가 false면 "일부 미확인"을 함께 표시한다(거리가 없는 산책은 합계에서 빠진다) |
| 함께한 강아지 | `history_unique_dog_count` | 10-1 카드 |
| 레벨 | `level` | 10-1 배지. 서버가 평가해 올리는 값이다 |

- 총 시간(`total_duration_seconds`)은 표시하지 않는다.
- 이전 봉사 기록 합계(`total_walk_count`, `total_distance_m`, `unique_dog_count`)는 화면에 쓰지 않는다.
- 레벨 반영 산책 수를 `total_walk_count`나 `history_walk_count`로 추정하지 않는다. 레벨은 서버의 평가 결과만 따른다.
- 기기 확인: 9-1 카드는 위 필드로 바꿨고 아직 기기에서 확인하지 않았다. 10-1은 9단계에서 같은 필드로 연결한다.

`MockSession`과 `src/data/*`는 더 이상 쓰는 곳이 없어 삭제했다.

- 10-1 마이페이지: 닉네임(`GET /users/me`), 통계 카드(`history_walk_count`, `history_distance_m`, `history_unique_dog_count`), 레벨(`level`),
  거리 일부 미확인 표시(`history_distance_is_complete`가 false일 때), 로딩, 오류와 다시 시도, 당겨서 새로고침, 내 정보 수정에서 돌아오면 닉네임 갱신
- 10-2 내 정보 수정: 프로필 불러오기, 닉네임 변경 저장, 이름 변경 저장(온보딩 Step 1을 마친 계정), 바뀐 필드만 전송, 저장 응답 뒤에 화면 닫기
- 10-2 번호 변경 전 과정: 새 번호 입력, 인증 요청(`/users/me/profile/phone-verifications`), 인증번호 확인, 저장(`phone_number` + `phone_verification_id`)
- 10-2 번호 변경 오류: 다른 계정이 쓰는 번호(409 `PHONE_ALREADY_REGISTERED`), 인증 없이 저장(409 `PHONE_VERIFICATION_REQUIRED`),
  틀린 인증번호(422 `VERIFICATION_CODE_INVALID`), 만료(410), 15분이 지난 인증, 닉네임 중복(409 `NICKNAME_ALREADY_EXISTS`)
- 10-2 버전 충돌(409 `PROFILE_VERSION_MISMATCH`): 최신 프로필을 보여 주고 "서버 값 보기 / 내 입력으로 저장 / 닫기"를 고르게 하는지(조용히 덮어쓰지 않는다)
- 10-3 산책 선호: 불러오기(저장값 없으면 온보딩 값), 저장, 버전 충돌(409 `PREFERENCE_VERSION_MISMATCH`)과 선택 화면, 저장 응답 뒤에 화면 닫기
- 설정 화면: "목업" 문구가 없는지, 로그아웃 행
- 로그아웃(마이페이지와 설정): 서버 호출 뒤 토큰과 로컬 상태 삭제, 로그인 화면 이동, 같은 계정으로 다시 로그인했을 때 이전 상태(산책, 예약, 이력, 임시 입력)가 남지 않는지
- 로그아웃 중 서버에 닿지 않을 때(비행기 모드): 이 기기에서만 로그아웃했다는 안내 뒤에도 로컬 상태가 지워지는지
- 산책 중이고 보내지 못한 위치 기록이 있을 때 "그래도 로그아웃 (미전송 기록 삭제)" 확인이 한 번 더 뜨고, 그것을 고르면 로그아웃되는지.
  그 밖의 경우(산책 중이어도 보내지 못한 기록이 없을 때 포함)는 확인 한 번으로 바로 로그아웃되는지
- 본 레벨업 기록(`levelUpSeen`)이 로그아웃 뒤에도 계정별로 남는지

### 통계 매핑 적용
10-1은 위 "통계 필드 매핑(확정)"과 같다: 총 산책 `history_walk_count`, 총 거리 `history_distance_m`(미확인 표시 포함),
함께한 강아지 `history_unique_dog_count`, 레벨 `level`. `total_*`와 `total_duration_seconds`는 쓰지 않는다.

### 테스트 데이터 준비
현재 로컬 DB: 봉사자 `snsns`(닉네임 `eksks`, 번호 010-0000-0001, 프로필 버전 1), 보호소 `shelter01`. 산책 선호는 아직 저장된 행이 없다(버전 0).
번호는 합성 번호 010-0000-0000~9999만 쓸 수 있고, 로컬 BE의 고정 인증번호는 `123456`이다(`SMS_MOCK_FIXED_CODE`).

1. 번호 변경 성공: 새 번호 `010-0000-0002`로 변경한다(인증번호 `123456`). 변경 뒤 10-2에 새 번호가 보이고 프로필 버전이 올라가야 한다.
2. 다른 계정 번호 409(`PHONE_ALREADY_REGISTERED`): 두 번째 봉사자 계정이 번호 `010-0000-0003`을 갖게 만든 뒤, 첫 번째 계정에서
   `010-0000-0003`으로 인증을 받고 저장한다. 인증 요청과 확인은 통과하고 저장에서 409가 나와야 한다(`#110` 정책).
   두 번째 계정 만들기(Swagger, 모두 이 앱의 가입·온보딩과 같은 API):
   - `POST /users/` `{"login_id":"second01","nickname":"second_user","password":"<15자 이상, 대소문자·숫자·특수문자 포함>",
     "privacy":{"document_version":"privacy-test-v1","age_14_plus_confirmed":true,"collection_use_agreed":true,"ai_overseas_transfer_agreed":false}}`
   - `POST /auth/login` `{"identifier":"second01","password":"..."}` 로 토큰을 받아 Authorize에 넣는다.
   - `PUT /users/me/pledge` `{"pledge_version":"pledge-local-v1"}`
   - `POST /users/me/phone-verifications` `{"phone_number":"010-0000-0003"}` → 응답의 `verification_id`
   - `POST /users/me/phone-verifications/confirm` `{"verification_id":"<위 값>","code":"123456"}`
   - `PUT /users/me/onboarding/basic-info` `{"full_name":"홍길동","birth_date":"1995-05-05","phone_verification_id":"<위 값>"}`
   위 본문은 FE 코드와 BE 스키마를 읽어 정리한 것이며 실제로 호출해 확인하지는 않았다. 정책 변수가 다르면 `PRIVACY_DOCUMENT_VERSION`, `PLEDGE_CURRENT_VERSION`을 BE `.env`에서 확인한다.
3. 프로필 버전 충돌: 앱에서 10-2를 연 채로, Swagger에서 첫 번째 계정(`snsns`) 토큰으로 `GET /users/me/profile`을 읽어 `profile_version`을 확인한 뒤
   `PATCH /users/me/profile` `{"expected_profile_version":<현재 값>,"nickname":"conflict_nick"}`을 한 번 보낸다. 앱에서 다른 값을 고쳐 저장하면 409가 나와야 한다.
4. 선호 버전 충돌: 앱에서 10-3을 연 채로 Swagger에서 `PATCH /users/me/walk-preferences` `{"expected_version":0,"duration_code":"OVER_60_MIN"}`을 한 번 보낸다
   (저장된 행이 없어 버전 0이다). 앱에서 저장하면 409가 나와야 한다.
5. 닉네임 중복: 앱에서 10-2 닉네임을 `second_user`(두 번째 계정)로 바꿔 저장하면 409(`NICKNAME_ALREADY_EXISTS`)가 나와야 한다.


### 문서와 코드 차이 (BE 담당자에게 알릴 것)
- **프로필 번호 인증 경로:** 문서(`docs/HANDOFF-FE.md` 4.7, 5절)는 `/users/me/phone-verifications`라고 적었지만, 그것은 온보딩 인증 경로다.
  프로필 번호 변경은 `POST /users/me/profile/phone-verifications`(발송)와 `POST /users/me/profile/phone-verifications/confirm`(확인)을 쓴다.
  FE는 코드 기준인 프로필 경로를 쓴다. 문서의 "프로필 번호 변경도 같은 방식"이라는 문장이 경로까지 같다는 뜻으로 읽히지 않게 고쳐야 한다.
- **문서에 없는 오류 코드:**
  - 프로필 `PATCH`: 403 `PROFILE_UPDATE_NOT_ALLOWED`, 409 `PROFILE_BASIC_INFO_REQUIRED`, 422 `INVALID_PROFILE_PAYLOAD`, `NICKNAME_REQUIRED`, `REQUIRED_FIELD`
    (문서는 `PROFILE_VERSION_MISMATCH`만 적었다. `NICKNAME_ALREADY_EXISTS`, `PHONE_VERIFICATION_REQUIRED`, `PHONE_ALREADY_REGISTERED`도 코드에만 있다)
  - 프로필 인증 확인: 422 `INVALID_VERIFICATION_PAYLOAD`
  - 선호 `PATCH`: 403 `PREFERENCE_NOT_ALLOWED`, 422 `INVALID_PREFERENCE_PAYLOAD`, `INVALID_DURATION`
    (문서는 `PREFERENCE_VERSION_MISMATCH`만 적었다. 코드에서는 저장값이 같아도 버전이 다르면 409다)
- **선호에는 지역이 없다:** 코드의 선호는 `duration_code`와 `size_code`뿐이고, `region_code` 등 다른 필드를 보내면 422다.
  FE의 10-3은 지역을 저장하지 않고 "온보딩에서 고른 지역"이라는 고정 문구만 보여 준다. 문서의 지역 관련 설명(과 Notion 일부 명세)을 코드에 맞춰야 한다.
